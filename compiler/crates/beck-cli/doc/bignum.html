Big

model Big

An integer of any size.

`Big(negative=false, limbs=[])` is zero, and it is the only representation of zero: a negative zero would compare unequal to a positive one under `==`, and a library whose zero has two values is a library whose tests pass and whose folds do not.

Division

model Division

A quotient and a remainder together, because long division computes both and a caller that wants both should not pay for it twice.

The signs follow `Int`: the quotient truncates toward zero and the remainder takes the sign of the dividend, so `divide(big(-7), big(2))` is `-3` remainder `-1` and `-7 / 2` and `-7 % 2` say the same.

big

big(n: Int) -> Big

defon anyno effects

An `Int` as a `Big`. Total — including the most negative `Int`.

The limbs are peeled off the *signed* value rather than from `abs(n)`, which is not a micro-optimisation: `abs` of the most negative `Int` overflows and there is no positive `Int` to hold it, so a conversion written the obvious way has exactly one input it cannot take. `%` follows the sign of the dividend, so a negative `n` gives negative limbs and `negate` on each one is enough.

big_of_str

big_of_str(text: Str) -> Big

defon anyraises(BigError)

Read an optionally-signed run of decimal digits. Anything else raises.

Leading zeros are accepted and normalised away — `"007"` is seven — because a leading zero is a way of writing a number and not a different number. An empty string, a bare `"-"`, a space and a `"1_000"` are all `NotANumber`: this is a reader for a canonical form, and `docs/46` §46.2's rule is that a parser raises rather than guessing.

A `Big` as an `Int`, or nothing when it does not fit.

`None` rather than a raise, and rather than a saturating answer: narrowing is a question with a "no", not a failure of the program, and a caller that wants a failure writes one line.

big_to_real

big_to_real(b: Big) -> Float

defon anyno effects

A `Big` as a `Float`. **Lossy**, and named so a reader has to mean it.

A real has 53 bits of significand, so any `Big` above 2⁵³ is rounded — and one above about 1.8 × 10³⁰⁸ becomes an infinity, because that is what IEEE 754 does and `docs/32` §32.3 declines to lay a rule of Beck's on top of the format's own.

compare_big

compare_big(a: Big, b: Big) -> Int

defon anyno effects

`-1`, `0` or `1`, by value.

Written rather than left to `<`, because `<` on a record compares field by field and `Big`'s first field is the *sign flag* — so `-5 < 3` would be decided by `false < true` and come out backwards. `docs/50` §50.5 found the same edge from the other side, and `docs/54` is the write-up; here it is a reason to expose an ordering function and say why.

divmod_limbs

divmod_limbs(a: list[Int], b: list[Int]) -> LimbDivision

defon anyno effects

Schoolbook long division, most significant limb first.

The trial quotient is found by **binary search** rather than by Knuth's estimate-and-correct. That is fourteen comparisons per limb instead of one multiply and a rare fixup, so it is slower — and it is obviously right, which for a first implementation of division is the trade to make. `docs/55` §55.6 records it as the thing to replace if this is ever a bottleneck.

int_bound

int_bound(negative: Bool) -> list[Int]

defon anyno effects

The largest magnitude an `Int` holds: 2⁶³ - 1 positive, and one more than that negative, because two's complement is not symmetric. The positive bound is written as a literal because it *is* one; the negative bound is that plus one because the literal for it does not exist.

to_int_from

to_int_from(b: Big, i: Int, acc: Int) -> Int

defon anyno effects

Horner's rule from the top limb down, accumulating **negative** for a negative value.

Accumulating the magnitude and negating at the end would overflow on exactly one input — the most negative `Int`, whose magnitude is not an `Int` — which is the same asymmetry `big` deals with at the other end, and the same fix.
