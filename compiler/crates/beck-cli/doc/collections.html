Set

type Set = newtype[Map[?1000000, Bool]]

A set of `T`, as the keys of a map.

The value is `Bool` and is always `true`: what a set stores is the *key*, and `Map` is the only ordered keyed collection the host provides. Membership is therefore the map's lookup rather than a scan, which is the whole reason to have this type rather than pass a `list[T]` around and call `list_contains`.

Pair

A pair, for the two-key sort above and for anything else that wants an order over two things.

`left` and `right` sort in that order because `l` comes before `r`, not because they are written in that order — see `sorted`.

group_by

group_by[T, K](xs: list[T], key: (T) -> K) -> Map[K, list[T]]

defon anyno effects

Everything in `xs`, filed under `key(x)`, each group in the order it was read.

`key` may do anything a function may do: if it can fail, `group_by` can fail, and the row says so without this signature mentioning one (`docs/27`). That is the property that lets a library take a function at all without deciding on its caller's behalf what a function is allowed to be.

index_by

index_by[T, K](xs: list[T], key: (T) -> K) -> Map[K, T]

defon anyno effects

Everything in `xs` by its key, with the last one winning.

Last rather than first because that is what a fold over a log means: a later event about the same id is the one that is true. A caller who wants the first reverses the list.

min_of

min_of[T](xs: list[T]) -> Option[T]

defon anyno effects

The smallest and largest, in one pass.

These were `list_get(sorted(xs), 0)` and its mirror, which is `n log n` and a copy of the whole list to answer a question about one element of it. `list_min` and `list_max` are primitives for the reason the rest of the collection algebra is: the incremental view engine maintains what it can see, and an aggregate written as a sort is a sort (`docs/99` §99.9 item 6).

Neither takes a comparator, for `sort_by`'s reason one level down: a caller who wants the smallest *by* something has a key, and `sort_by` plus a head is that. What these answer is the smallest, which `Value`'s own total order already decides.

sorted

sorted[T](xs: list[T]) -> list[T]

defon anyno effects

Sorted by the values themselves.

`sort_by` takes a key rather than a comparator, and this is the key that is the value. Sorting by two things is one key function returning a record: `lambda r: Pair(left=negate(r.score), right=r.name)` is "by score descending, then by name", and needs no comparator to say so.

**A record compares by field name, in order, and not in the order the fields are declared.** A value carries its fields and not its declaration, so the runtime has nothing else to sort them by — and a rule the checker applied instead would disagree with the order the same records come back from `elements`, which is this one. So a key record whose first priority is a field called `score` and whose second is called `name` sorts by the **name**, silently and correctly. Naming the fields is how a two-key sort says which key is first, which is why `Pair`'s are `left` and `right`.

unique

unique[T](xs: list[T]) -> list[T]

defon anyno effects

`xs` with later duplicates dropped, in the order they were first seen.

This is a different function from `elements(set_of(xs))`, which is also duplicate-free and is *sorted*. Both are wanted and neither is the other: a menu keeps its order, a set of tags has no order to keep.
