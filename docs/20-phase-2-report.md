# 20 — Phase 2 report: effects and placement

Phase 2 of [`08-roadmap.md`](08-roadmap.md) is headed **"The moat."** It asks for effect rows and
their inference, placement inference with a cost solver, the `secret[T]`/`Sendable` machinery with
§3.5's security properties as executable tests, `.becki` published signatures with separate
compilation — "**do not slip this**; it is the historical failure mode" — and boundary versioning.

All of it is built. **The exit criteria are met**, and §20.3 says with what evidence:

> **Exit**: on a corpus of 20+ programs, placement is inferred with no annotations for the common
> cases; every §3.5 property is a passing test; a 3-module project rebuilds incrementally without
> recompiling dependencies whose signatures didn't change.

The headline: **strip every `@on(...)` from the todo sketch and it still compiles, places and
runs** — `ingress` on the server, the fold at the data tier, the page at the browser, and all nine
pure definitions unplaced so they compile to whichever tier calls them. Across the 22-program
corpus, 44% of everything placed is unplaced-pure.

Three things this phase is honest about rather than quiet about, and §20.5 has the full list.
**One item assigned to Phase 2 was not built**: the general slicer
([`19`](19-phase-1-report.md) §19.9 put it here, next to placement inference, because both are about
treating the graph as a graph). Native codegen is still not done, unchanged from Phase 1. And the
placement solver decides *less* than §3.4 implies — for a reason that is the design working rather
than the solver shirking, §20.4 item 1.

## 20.3 The exit criteria

### "Placement is inferred with no annotations"

[`corpus/`](../compiler/corpus/) is 22 programs — 19 single-file and a three-module project — and
**none of them contains an `@on(...)`**, except one that says so in its own first line and exists
to check that an annotation wins. They are deliberately different programs: the accumulator varies
(a counter, a map of records, a map of maps, a list), and so does the effect row — `cap.*` for
authority, `env` and `secret[T]` for credentials, `net.out` for a named host *and* for the own
origin, `external.read` for an escape hatch, `log`/`metrics` for ambient, `nondet` for ids and
clocks.

The canonical program, with its annotations stripped:

```console
$ sed 's/^@on(server)$//;s/^@on(data)$//;s/^@on(client)$//' examples/todo.beck > bare.beck
$ beck explain place bare.beck
name                 tier     kind       effects
apply_event          any      definition {}
toggled              any      definition {}
validate             any      definition {}
if_owned             any      definition {}
mine                 any      definition {}
remaining            any      definition {}
view                 any      definition {}
render               any      definition {}
done_class           any      definition {}
proposals            server   signal     {ingress}
events               data     signal     {}
todos                data     signal     {durable}
page                 client   signal     {}

Solved exhaustive (optimal for this cost model); total cost 81.8.
```

and one decision, interrogated:

```console
$ beck explain place bare.beck todos
todos  →  data tier

  effects    : {durable}
  candidates : client (cannot discharge this row), server (cost 189.3), data (cost 81.8)
  chosen     : data
  because    : the log is at the data tier, and the accumulator is what the log stores
```

Where the corpus ends up, across 168 placed definitions and signals:

| tier | count | share |
|---|---|---|
| `any` (unplaced-pure) | 74 | 44.0% |
| `server` | 51 | 30.4% |
| `data` | 24 | 14.3% |
| `client` | 19 | 11.3% |

The first row is the interesting one. §3.3 says "purity means *unplaced*: legal on every tier,
compiled to each tier that needs it. That duplication is the payoff, not waste." Forty-four per cent
of the corpus is code that has no tier — including every fold function, which is what will let a
Phase 3 client apply an event optimistically using the same code the server folds with.

The harness asserts *placements*, not compilation: "22 programs compiled" would be true of a
compiler that put everything on the server. It names them — `03-billing.beck`'s `charge` on the
server because of `net.out(payments.example.com)`, `08-audit.beck`'s `audited` unplaced because
`log` is ambient, `02-chat.beck`'s `mine_only` on the server because it needs a session.

### "Every §3.5 property is a passing test"

[`security.rs`](../compiler/crates/beck-cli/tests/security.rs) — 18 tests over the eight rows of
§3.5's table, each written as the program a mistaken author would write:

| §3.5 property | how it is tested | result |
|---|---|---|
| Secrets cannot reach the browser | a `secret[Str]` in a command union; buried three records deep in the state; a `@on(client)` on a function that holds one | refused, B0410/B0401 |
| Clients can only *propose* | four forged frames the protocol has no representation for; an over-posted field that leaves no trace in the decoded value | refused / ignored |
| Authority is one chokepoint | events built by `filter_map` instead of `decide`; a `cap.admin` outside the validator | refused, B0504/B0412 |
| The log and rules never ship to clients | `@on(client)` on the fold and on ingress; the client bundle searched for seven server-side names | refused, B0401; bundle clean |
| No injection / no XSS | a todo whose text is a `<script>` tag; an attribute that tries to close its own quote; the rendered view searched for script | escaped; no script emitted |
| Least-privilege infra, computed | the egress policy with and without a `net.out`; the database grant | one effect, one rule; `SELECT, INSERT` |
| No arbitrary build-time code | a macro reaching for `read_file`; a macro trying to capture a caller's binding | unresolved; hygiene holds |
| Tamper-evident history | the `LogStore` trait's method list | append and read, nothing that edits |

The diagnostic quality is part of the property, not incidental to it. §3.5 requires "a compile error
**naming the flow**", so the test asserts the path:

```console
error[B0410]: `Command` is what clients send, so it must be Sendable
  --> todo.beck:126:1
    |
126 | proposals: Stream[Proposal] = merge_clients()
    | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ `secret[Str]` reaches it at `Command.Authenticate.token`
    |
  = note: `secret[T]` is deliberately not Sendable: that is the whole mechanism
  = note: a command is minted in the browser: a secret in one would be a secret the browser already had
```

The caret sits on the ingress declaration rather than on the union, which is the weakest of the
Phase 2 diagnostics and is named here rather than left to be found: the *path* is right and the
*span* is a stand-in. `Command` has no single declaration site the checker holds at that point,
because the boundary is a property of the program's wiring. Worth fixing when types carry their
declaration spans.

### "A 3-module project rebuilds incrementally"

[`corpus/project/`](../compiler/corpus/project/) is a domain, a policy over it, and the app that
wires them. `beck check app.beck` resolves both imports, checks each module against the others'
*interfaces*, links the bodies and slices the result — and the app serves its page.

Measured through the Salsa spine:

| | time | modules re-checked |
|---|---|---|
| cold | 1.20 ms | 3 |
| after a one-line body edit in `domain` | 0.25 ms | **1** |
| after widening an effect in `domain` | — | 3 |

The middle row is §3.6's firewall as a number. `checked(m)` depends on `interface(d)` for each
import and never on `source(d)`; a body edit recomputes `interface(domain)`, it compares *equal* to
what it was, Salsa backdates it, and nothing above it re-runs. The third row is what makes the
second mean something: a firewall that never lets anything through is a wall.

The honest bound is stated in the test rather than discovered later: **the firewall is per module,
not per item.** `policy` never calls the widened function, but it imports the module whose interface
moved, so it is re-checked. §4.6's query list says `signature(item)`; narrowing from a module to an
item costs nothing here, where a module is one file, and is what a 50 kLOC project would need.

### And it still runs

Everything Phase 1 proved still holds, on the same commands: `beck run` serves the compiled sketch,
`beck replay --verify` reproduces its state, and the differential, replay-determinism, backend-seam
and scaling harnesses are green. Placement inference is not a separate compiler.

## 20.4 What turned out harder than expected

In rough order of how much it changed the design.

### 1. The solver decides less than §3.4 implies, and that is the design working

§3.4 describes a min-cut over the call-and-signal graph choosing among tiers. Building it made
clear that **three rules pin most of a program before any cost is computed**, and each is a
statement about *meaning* rather than about cost:

1. `@on(...)` wins (§3.3, explicitly).
2. A **pure definition is unplaced** and compiled into every tier that calls it. That is 44% of the
   corpus, and it is not a placement decision at all — it is the absence of one.
3. A **`Signal[Html]` is the browser's subscription** (§4.3: "every signal edge that crosses tiers
   becomes a subscription… the client side a resumable `(subscription, seq)` consumer"). What the
   type means, not what it costs.

What remains genuinely open is: which tier holds a `durable` fold, where `decide` sits, and where an
effectful definition that more than one tier could discharge ends up. Across the corpus that is 4–8
nodes per program, which is why exhaustive enumeration is not just adequate but *optimal* — the
solver proves its answer rather than converging on one.

The most interesting deferral is one §3.4 raises directly: "placing `view` server-side means the
crossing carries **DOM patches**; placing it client-side means it carries **data patches**.
Rendering placement is just another placement decision." It is not, yet, and pretending otherwise
would have been the wrong kind of completeness: **Mode B does not exist**, so there is exactly one
way to render and a cost model with one option is not choosing. What Phase 2 does instead is make
the model *ready* for the choice — a crossing is charged the **smaller** of its two endpoints'
values, because a compiler free to compute on either side will send whichever is less. Today that
minimum is a prediction; in Phase 3 it becomes the decision.

### 2. Effect inference had to be inference, not collection — and Phase 1's version had a hole

Phase 1 collected effects by walking a body and consulting each callee's **declared** row. An
intermediate that declared nothing hid everything behind it:

```python
def mint() -> Str:          # declares nothing
    return uuid()           # …and mints an id

def label(prefix: Str) -> Str:
    return prefix + mint()  # Phase 1: {} — Phase 2: {nondet}
```

That is not a simplification of inference; it is a hole in the determinism rule. A fold reaching
`uuid()` two calls deep passed Phase 1 and is refused now (`place.rs`'s
`a_fold_that_reaches_nondeterminism_two_calls_deep_is_rejected`).

Two things had to be right for the replacement to work, and neither was obvious in advance:

**A reference is not an application.** Phase 1's walk treated a *mention* of a function as
performing its effects, which would make `fold(apply_event, …)` effectful merely because
`apply_event` appears in it. Rows are latent on the type and charged when a function is applied.

**Rows subsume; they do not unify.** Equality would make a pure lambda fail to match
`(a -> b ! e)`, and would make one higher-order definition unusable at two call sites with different
arguments. §3.1's "no subtyping beyond effect-row subsumption" turns out to be doing real work: it
is the exception the whole standard library rests on.

### 3. `time` and `rand` cannot be ambient — a correction to §3.2

§3.2 files `log`, `time`, `rand` and `metrics` under an ambient set "implicitly available *outside
folds* and elided from signatures". Phase 2 keeps `log` and `metrics` there and takes `time` and
`rand` out, and the reason is §3.3's own table: **the fold engine is a tier**, and whether a tier
discharges time and randomness is precisely §3.7's determinism rule. An effect that decides a
placement cannot also be elided from the signature the placement is derived from.

They stay as one atom, `nondet`, which `client` and `server` discharge and `data` refuses. The
practical consequence is visible in the corpus: `19-clock.beck`'s `stamp` reads a clock and is
placed on the server *by the same machinery* that places a `net.out`, rather than by a special case
in a determinism lint.

The correction has a pleasing side effect. `Tier::Any` is now defined as the **intersection** of the
concrete tiers, so "an ambient effect never forces a placement" and "`durable` always does" both
fall out of one line instead of being two special cases.

### 4. The operation id never moved, and §4.3 exists to stop exactly that

§4.3 asks for "a stable, content-derived operation id — *not* a URL a human maintains, and stable
across refactors that don't change the signature", and says what goes wrong without it: "the deploy
worked but every open browser tab broke."

Phase 1's id hashed the module name and the *names* of the command, event and state types. So it was
stable across a refactor — and stable across **adding a field to a command**, which is the change
that breaks every open tab. The defect was invisible until `--wire-compat` was built and reported a
breaking change against a release whose operation id was identical.

The id now hashes the three types **structurally**, transitively through every field of every
variant they reach, and a test pins both directions: a body edit leaves it alone, a field added to a
command moves it.

### 5. Capability discharge is a whole-program property, and only multiple modules showed it

Run per module, §3.5's "a `cap.*` effect that goes undischarged is a compile error" reported *every
correctly factored authority module as a violation* — because the chokepoint is one `decide` node
and it lives with the wiring, not with the policy.

The fix is a distinction the single-file phases could not have found: **boundary** checks are per
module (a module that puts a secret in something the client subscribes to is wrong on its own
terms), and **capability discharge** is per program, run once after linking, and only when the
program has a chokepoint at all. A library that holds `cap.session` is not a violation; it is a
library.

### 6. A `.becki` should be Beck, not a second notation

§3.6 sketches an interface syntax of its own — `orders : Signal[Map[OrderId, Order]] ! { durable }
@on(server)`. Writing a parser for it would have been a second grammar to keep in step with the
first, for a file whose entire purpose is to be reviewed by humans who already read Beck.

A `.becki` is instead ordinary Beck, using a **bodyless `def`** for each published name. The single
parser change it needed is a *declaration*, which the language wanted anyway — a trait's method
signature is one — and everything downstream came free: the lexer, the printer, `beck fmt`, the
diagnostics, and the round-trip property.

The interface's **digest** then needed one thing that was not obvious: row variables have to be
**closed** before publishing. Their numbering comes from the order the checker happened to mint
them, so two compilations of an unchanged module would publish different-looking contracts and the
firewall would never hold. The cost is named rather than hidden: effect polymorphism does not cross
a module boundary in Phase 2 — an exported higher-order function publishes its parameter's row as
closed, so an importer passing an effectful argument where the contract says pure is refused. That
is the sound direction, and it is the first thing to revisit if a real library runs into it.

### 7. Compatible does not mean unchanged, and events are not commands

The interesting content of `--wire-compat` is an asymmetry that is invisible in either type alone:

- a **new command variant is compatible** — no old client sends it;
- a **new event variant is breaking** — nothing old sends one either, but an old fold is still
  running during the rollout, and §3.1's exhaustiveness check means it has no case for it.

It comes from which side of the boundary each type crosses. Commands are written by old clients and
read by new servers; events are written by both versions and read by the log forever. Getting this
from one rule would have been wrong in one direction or the other.

Every classification carries the reason it was made, because a CI gate that says "breaking" and
nothing else gets switched off.

### 8. The CI workflow had never run

The largest finding of the phase, and it is not about the compiler.

`.github/workflows/compiler.yml` has been **invalid YAML since it was written**: a step name
beginning with a backtick, which YAML reserves as an indicator and refuses to start a plain scalar
with. GitHub Actions rejects the whole file rather than the line, so every gate in it — the
harnesses, clippy, the format check, the demo that runs — had been silently absent for the whole of
Phase 1.

[`19`](19-phase-1-report.md) §19.4 item 10 names this exact pattern one phase early, about
artefacts: "an artefact nobody has executed is a design document." **A CI workflow is an artefact.**

It found real things. Running the steps by hand showed that `beck fmt --surface sexpr` produced a
file `beck check` could not read — the printer emits `(module todo …)` and the reader wrapped it in
a second module — so the surface §2.2 calls canonical did not round-trip, which is the property
§4.8 puts first. Three smaller defects came out of the same afternoon: a module name was the file
name, so `01-counter.beck` printed a module form no reader could read back; a definition could be
named after a core form (`record`, `map`, `list`) and be silently shadowed by the syntax; and the
project pipeline built its own `SourceMap`, so a multi-module diagnostic crashed the renderer.

All are fixed, every workflow step has now been run locally, and
[`tests/workflows.rs`](../compiler/crates/beck-cli/tests/workflows.rs) is the narrow check that
would have caught it — it looks for the two characters YAML reserves and nothing else, because a
half-understood linter that fires on valid files gets deleted.

### 9. The data and server tiers are the same process, and the model says so

A `durable` fold with a `Map` accumulator goes to the data tier by a wide margin. One holding a
single `Int` does not care — and the cost model says so rather than inventing a difference.

That is correct for Phase 2, and worth stating because it looks like an equivocation. The charge for
keeping an accumulator away from the log is an edge to the log, sized from the accumulator; eight
bytes crossing between two tiers that are *the same process* costs approximately nothing, because it
is approximately nothing. The distinction becomes cost-separable in Phase 3, when the incremental
view engine and the SQL read models give the data tier its own address. Recorded as a test
(`a_big_accumulator_goes_to_the_data_tier_and_a_small_one_does_not_care`) rather than tuned away.

### 10. The properties §4.8 asks for found a defect the corpus could not

§4.8's testing table gives placement `proptest` and three properties: *no valid program is
rejected*, *no `secret` reaches client*, and determinism and stability "over generated programs".
Phase 2 nearly shipped with only the first kind of evidence — 22 programs that somebody wrote — and
the difference showed up immediately.

Generating random *source* is not the way: random text is almost never a program, and random
well-typed Beck needs a type-directed generator that would itself be a body of code to trust. What
[`placement_properties.rs`](../compiler/crates/beck-cli/tests/placement_properties.rs) generates is
the thing the solver reasons about — a call graph of definitions with random effect rows — emitted
into a real program that goes through the real pipeline.

The first run found that **a definition carrying `partial` was being placed when it should have been
unplaced**. The pin for §3.3's "purity means unplaced" tested *"the visible row is empty"*, and
`partial` is not ambient, so it survived that test — even though every tier discharges it. The right
test is `Tier::Any.discharges` over the whole row, which is what §3.3 actually says, and it is now
what the code says. Nobody would have written that program by hand: it takes a function that may
diverge and does nothing else, which is a shape a corpus of realistic programs does not contain.

It also sharpened one thing that was true but unstated: **a pinned node is not required to be at a
cost minimum.** `page` costs more on the client than on the server and belongs there anyway, because
a `Signal[Html]` is the browser's subscription. `Explanation` now carries `pinned` so that the
distinction between "decided by a rule" and "decided by a cost" is visible to a tool and not only to
a reader.

### 11. Inference is a tenth of a compile

The worry going in was that placement inference would dominate the front end. It does not:

| | µs |
|---|---|
| check (parse, expand, resolve, typecheck, infer rows) — 19-program total | 5 136 |
| solve (build the graph, enumerate, explain) — same 19 | 616 |
| solve as a share of both | **10.7%** |

The largest program in the corpus solves in 47 µs against 454 µs of front end. The exhaustive
search is not the cost; the front end is, which is what `beck-db`'s Salsa spine is already for —
the same conclusion [`19`](19-phase-1-report.md) §19.8 reached about the dependency graph.

## 20.5 What Phase 2 is not

- **No native codegen.** Unchanged from Phase 1 and still the largest gap: a `Core` evaluator stands
  in for Cranelift, behind the `Backend` seam. Nothing in Phase 2 depends on the evaluator, and
  `tests/backend_seam.rs` still drives the runtime through an implementation that is not it.
- **No row polymorphism on records.** §3.1 asks for it and models are still nominal. Effect rows are
  polymorphic; record rows are not.
- **No trait semantics.** `trait`/`impl` still parse and warn. Phase 1's warning said "trait
  resolution arrives with Phase 2's effect work"; it did not, and that sentence has been corrected
  rather than left to be discovered.
- **Effect polymorphism stops at a module boundary** (§20.4 item 6).
- **The firewall is per module, not per item** (§20.3).
- **No `@breaking` marker in the source.** §4.3 asks for one; `--wire-compat --breaking` is a flag
  on the command instead. The flag is checked in CI and the marker is not, so the property holds;
  the ergonomics of declaring it *in the program* are Phase 4's, with the deprecation shims.
- **No `migrate`/`upcast`.** §3.9's typed migrations are Phase 4's, and `--wire-compat` says so: a
  green run means "no old client breaks", not "this deploy is safe".
- **No cost measurement.** The numbers in [`cost.rs`](../compiler/crates/beck-core/src/cost.rs) are
  *ordered*, not measured: every one is a ratio the design already states, chosen so it can be
  argued with rather than tuned in the dark. `beck tune` (Phase 4) is where a measured number would
  replace a stated one, and `ASSUMED_CARDINALITY` is the single place a guess about invisible data
  is made.
- **The splitter still understands one topology, and this was assigned to Phase 2.**
  [`19`](19-phase-1-report.md) §19.9 says so explicitly: "`Roles` and the `Inliner` encode one
  topology — Phase 2 … a general slicer belongs with placement inference, since both are about
  treating the graph as a graph." Placement inference was built and the slicer was not. It is the
  one item this phase was handed and did not deliver, and it should be said first rather than last.
  What makes the narrowness survivable is unchanged from Phase 1: it announces itself, and
  `split.rs`'s `a_shape_the_splitter_cannot_slice_is_refused_rather_than_mis_sliced` pins the
  refusal. It is the first thing Phase 3 should pick up, because §5.3's incremental views need the
  graph treated as a graph too.
- **`beck explain query <fn>` and `beck explain cost <fn>` are not built.** §4.7 asks for both. The
  first has nothing to say until §3.8's incremental view compilation exists — the `Query`
  sub-language is deliberately symbolic and there is no plan to explain — and it belongs with Phase
  3. The second is largely served by `beck explain place <name>`, which already prints every
  candidate's cost; whether a separate `cost` view earns its place is a question for when there is a
  second cost dimension to show.
- **No deprecated shims and no `beck.toml`.** §4.3's rule is "a removed operation is retained as a
  deprecated shim for N releases (declared in `beck.toml`)". `--wire-compat` reports a removal as
  breaking and stops there; retaining the old operation is Phase 4's, with the rollout choreography
  that needs it. There is no `beck.toml` at all yet.
- **`check.rs` grew from 1,702 lines to 2,166.** [`19`](19-phase-1-report.md) §19.9 said to watch
  it, and predicted where the pressure would come from: "it is also the file Phase 2's effect
  inference must open, so if the one-pass decision is going to stop paying, that is when it will
  show." It has not stopped paying — resolve, typecheck, lower and infer are still one coherent
  walk, and the effect work added a row accumulator rather than a stage — but 27% growth on the
  largest file in the compiler is the number to watch, not a comfort.
- **No Mode B, no incremental views, no migrations, no operator, no identity beyond a dev-mode
  actor, no `beck fork`, no package system, no LSP, no playground.** All Phase 3 and beyond.

## 20.6 What this changes for Phase 3

1. **The cost model is ready for the Mode A/B decision and cannot make it.** §20.4 item 1: a
   crossing is already charged the smaller of its two ends, which is exactly the choice §5.1
   describes. Phase 3's Mode B turns a prediction into a decision, and the solver needs no new
   machinery for it — only a second lowering to choose between.
2. **`per_session` is the fanout point, and it is a node.** Placement now sees it as one, which is
   what §5.3's shared-prefix plans will need: the arrangement is shared up to the `per_session`
   edge and specialised after it.
3. **Effects already name the incrementalisable set.** A view whose row is empty is a pure function
   of the signal — which is §3.8's precondition for compiling it to a differential-dataflow plan.
   `beck explain incremental <view>` has its input already.
4. **The per-item firewall is the next increment, and it is cheap.** §4.6 asks for
   `signature(item)`; Phase 2 has `interface(module)`. At one file per module the difference does
   not show; at 50 kLOC it is the difference between a keystroke and a coffee.
5. **A workflow is an artefact.** §8.3's "every phase ships a demo that runs" should be read as
   applying to the thing that runs the demo. Phase 3 should start by executing its own gates once
   by hand.
6. **The general slicer is the debt this phase leaves.** §20.5's first item: it was assigned to
   Phase 2 and not built. §5.3's incremental views need the signal graph treated as a graph, so
   Phase 3 pays for it either way — better deliberately than by discovering the splitter refuses the
   program the new view engine wants.
7. **The `data`/`server` distinction needs a second address to be worth solving.** §20.4 item 9.
   Until the incremental view engine is a separate thing, half the solver's freedom is over a
   distinction with no consequence — which is fine, and worth knowing before reading too much into
   a placement.
