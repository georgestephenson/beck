# 99 — Phase 3 report, part 67: three of the supply-chain bullet's four pieces

**Built.** [`08`](08-roadmap.md)'s supply-chain bullet reads "`beck init ci`, apko image build
in-process, cosign signing, SBOM", and [`92`](92-sbom-report.md) built the fourth of those and named
the other three as untouched. All three are now built:

- **`beck image`** assembles an OCI image in this process — it resolves the packages the apko
  config names against the Wolfi index, fetches them, unpacks them, adds the toolchain and the
  program, and writes an OCI layout. No apko, no melange, no daemon, no `docker`, no registry
  client.
- **`beck sign`** and **`beck verify`** produce and check a Sigstore signature over the image
  manifest's digest, in the artefact shape and payload format `cosign verify --key` reads.
  `beck key generate` writes the key pair.
- **`beck init ci`** writes the workflow [`28`](28-releases-and-deployment.md) §28.3 specifies —
  check, test, wire-compat, build, then image and signature from the default branch.

What it is **not** is a release pipeline. Nothing pushes to a registry, nothing writes a provenance
attestation, and no release of this compiler has been cut; §99.6 is the list and §99.8 is what that
leaves Phase 3.

## 99.1 Why an image can be built here at all

The same property [`92`](92-sbom-report.md) §92.1 used to justify an SBOM before a pipeline, spent
a second time. [`06`](06-kubernetes-and-packaging.md) §6.2 chose apko because "the build performs no
arbitrary execution", and it drew the consequence for *reproducibility*. The consequence for
**implementation** is the one this work rests on: a build with no arbitrary execution has nothing in
it that a compiler cannot do. There is no `RUN` line to interpret, no build container to start, no
shell. What is in the image is packages plus two files, so the build is

```text
packages + two files → one tar → three JSON documents
```

and every step of that is ordinary code. §6.2's own implementation note called this — "move to
writing the OCI layout directly from Rust … once the format is settled, so `beck build` is one
process with no external tools" — and listed `oci-client`/`oci-spec` as the way. Neither is used:
the OCI image format is four JSON documents and a tar, and the documents are shorter than the
schema types for them would be.

**The melange step is gone from the in-process route, and the reason is worth stating precisely.**
apko cannot copy from the host — that absence *is* its reproducibility story — so the binary has to
be packaged first ([`19`](19-phase-1-report.md) §19.5 is the defect that taught this project so).
A build that *is* the compiler has the binary and the program in hand and copies two named files
whose digests it prints. That is not a hole in the argument, because the argument was never about
copying: it is about **execution**, and this build executes nothing either. The apko and melange
configs are still emitted, because they are the image's *description* — what a reader checks, and
what somebody who would rather use apko runs.

## 99.2 One source, four artefacts, and the gates that hold them together

[`92`](92-sbom-report.md) §92.2's rule was: an inventory assembled beside the thing it describes is
an inventory that can be wrong about it, so render both from one function and read the *rendered*
output back. There are now four things that must agree about one image, and each has a gate that
reads a rendering rather than calling a function twice.

| What must agree | The one source | The gate |
|---|---|---|
| The package list — SBOM, apko config, and what `beck image` resolves | `sbom::packages` | `supply_chain.rs` §"the_bill_of_materials_lists_what_the_image_config_installs" |
| The two files the application contributes, and their modes | `INSTALLS` | `supply_chain.rs` §"the_melange_package_installs_the_files_the_in_process_build_writes" — parses the emitted melange pipeline |
| The account the image runs as — apko `accounts:`, `/etc/passwd`, the OCI `User`, the pod's `securityContext` | `NONROOT` | `supply_chain.rs` §"the_image_config_and_the_pod_run_as_the_same_account", and `image.rs` for the passwd file |
| The process the image starts — apko `entrypoint:`/`cmd:`, the OCI `Entrypoint`/`Cmd` | `command()` | `image.rs` §"the_image_starts_the_process_the_apko_config_describes" — parses the emitted apko YAML |

The account row is the one that had a real defect waiting in it. Four artefacts named `65532`, three
of them generated by different code, and a mismatch between the image and the pod is the classic
"works locally, `CrashLoopBackOff` in the cluster" — invisible in review because each file is
correct on its own.

## 99.3 What checks this, other than this

A tar writer tested by its own reader agrees with itself; a signature checked by the library that
made it establishes that the library is self-consistent. Both were available failure modes here, so
neither is how the work is gated:

- **The system `tar` is on both sides.** The package fixtures in `image.rs` are built by `tar czf`
  and read by `beck_infra::apk`; the layer this project writes is then listed **and extracted** by
  `tar xzf`, and the extracted program is compared byte-for-byte against the source. A tar this
  project could write and only this project could read would pass a self-test and fail in a
  container runtime.
- **`openssl` verifies the signature.** `openssl dgst -sha256 -verify` reads the public key PEM and
  the DER signature — the same two things `cosign verify --key` reads — and the test also asserts it
  **refuses** a forged payload, because a verifier that accepts everything would pass the positive
  half.
- **A real APK, not only a fixture.** A fixture built by `tar czf` is one gzip member; a Wolfi
  package is three concatenated. `image.rs` §"a_real_package_reads" runs against a package a build
  actually fetched, and the CI job fetches one so `BECK_REQUIRE_APK=1` can forbid the skip.
- **Somebody else's YAML parser reads the generated workflow.** `init_ci.rs` parses it with
  `serde_norway`, for the reason `manifests.rs` already does.

Both external tools **skip loudly** when absent — `BECK_REQUIRE_TAR=1` and `BECK_REQUIRE_OPENSSL=1`
forbid the skip, and CI sets both.

### The gate that only a generator needs

`init_ci.rs` §"the_workflow_runs_no_command_the_binary_does_not_have" reads every `beck <word>` out
of the emitted workflow and asserts each is a subcommand `beck --help` lists. A hand-written
workflow that names a renamed command fails once, in this repository, where somebody sees it; a
*generator* that does it fails on the first run in every repository that ran `beck init ci`. The
gate was checked by making it red: renaming one invocation to `beck imagine` fails it with the list
of commands that do exist.

## 99.4 Reproducible, and exactly how far

Two builds of one program from one package set produce a byte-identical index, manifest, config and
layer. That is asserted three times over: in `image.rs` against fixtures, in the CI job against the
real repository, and — in the direction a constant would satisfy — by changing the program and
asserting the layer digest **moves**. [`28`](28-releases-and-deployment.md) §28.2 item 3 asked for
"build the image twice, `diff` the digests" as a per-release gate; it is a per-commit one.

The limit, stated rather than left to be discovered:

| Claim | Holds |
|---|---|
| Same inputs, same digest, same machine, same toolchain | **Yes**, and gated |
| Same inputs, same digest, a different machine | **Yes** for the uncompressed layer (`diff_id`); for the compressed digest, only if `flate2` is the same version — a compressor may emit different valid output ([`0025`](adr/0025-deflate-so-the-image-build-needs-no-tools.md)) |
| Same *program*, same digest, a week later | **No.** apko resolves `tzdata` to whatever version the repository serves today, and so does this. That is [`92`](92-sbom-report.md) §92.5's version gap seen from the other side, and §99.7 says what would close it |

Nothing here reads a clock. No `created` on the config, no `created` in the history entry, mtime
zero on every tar member, and the gzip header's mtime and OS bytes written as constants — the same
discipline [`92`](92-sbom-report.md) §92.4 applied to the SBOM's serial number, for the same reason:
a document stamped with the time of day cannot be compared with `cmp`.

## 99.5 The signature says one thing, and it is worth being exact about which

The payload is Sigstore's simple-signing document, and signing it asserts that **the holder of this
key says this digest is that image**. Three properties are gated, and the third is the one that
matters:

1. the signature verifies under the public key alone — a different key does not verify it;
2. the payload is a `cosign container image signature` and not some other document;
3. **the digest in the payload is the manifest digest in this layout**. A signature that verifies
   over somebody else's digest is a valid signature and a worthless one, and `beck verify` refuses
   the layout when they differ.

Signing a *tag* is refused outright: `sign::image` requires a `sha256:` digest, because a tag moves
and a signature naming one asserts nothing about what is deployed.

**Keyed, not keyless, and deliberately.** Sigstore's keyless flow needs Fulcio to issue a
certificate against an OIDC identity and Rekor to log it — two network services and a workload
identity, none of which this project has ([`28`](28-releases-and-deployment.md) §28.1: no release
has been cut). A signing path exercisable only by a pipeline nobody has run is
[`19`](19-phase-1-report.md) §19.4 item 10's design document wearing a feature's clothes. The keyed
half can be produced, verified and gated on a laptop, so it is the half that was built; the
transparency log is what turns it into SLSA's build track, and it is named as absent rather than
approximated.

The private key is written `0600` and read from `BECK_SIGNING_KEY` in CI, because a key on a command
line is a key in the process table. The format is PKCS#8 PEM rather than cosign's own
`ENCRYPTED COSIGN PRIVATE KEY` container: what a consumer must be able to read is the **public**
key, and that is a standard SubjectPublicKeyInfo — `openssl pkey -pubin` reads it, which is the
check that it is not this project's own dialect.

## 99.6 What `beck init ci` will not pretend

The generated workflow builds the toolchain with `cargo install --git`, because there is no released
`beck` to install ([`28`](28-releases-and-deployment.md) §28.1) and therefore no `setup-beck` action
to `uses:`. Emitting one would put a workflow that fails on its first run into every repository that
generated it. A gate asserts that every action it does name is a first-party `actions/` one.

Two more refusals are in the file itself. It grants `contents: read` and **not** `packages: write`,
because nothing in it pushes — a permission granted for something that does not happen is a
permission somebody will later use. And the image job is `if: github.ref == 'refs/heads/main'`,
because a signature made on a pull request is a signature over code nobody has approved.

## 99.7 What is not built

| | Status |
|---|---|
| An OCI image, assembled in-process, reproducibly | **built** |
| The package index, resolution, fetch and unpack | **built** |
| A cosign-shaped signature, and verification of it | **built** |
| `beck init ci` | **built** |
| **A registry push** | **not built.** `beck image` writes a layout to a directory; getting it to a registry is `skopeo copy` or `crane push` today. The registry API is the next thing here and it is the one that makes the signature reachable by a consumer, since cosign looks a signature up *in the registry* by its `sha256-….sig` tag |
| **A provenance attestation** | **not built**, and unchanged from [`92`](92-sbom-report.md) §92.5. SLSA v1.2's build track wants a builder identity and a transparency log; this repository has neither, and an in-toto statement signed by a key on a laptop would claim a build platform that does not exist |
| **The SBOM inside the image** | **not built.** `beck build` writes the bill of materials beside the manifests; nothing attaches it to the image as a referring artefact, which is what §6.2's "attach the SBOM" means |
| **Multi-arch** | **not built.** The index has one manifest and is the shape that grows; what is missing is not the format but a cross-compiled toolchain binary per architecture, which is a release fact rather than a compiler one |
| **Package versions and digests, pinned** | **not built**, and it is the same gap [`92`](92-sbom-report.md) §92.5 named. The resolver takes the highest version the index offers *today*; a lock file recording the resolved `(name, version, digest)` triple is what would make an image reproducible across weeks rather than across minutes, and it is the single highest-value item left in this bullet |
| **Version constraints, enforced** | **not built, and reported rather than silently ignored.** The resolver reads `foo>=1.2` and installs `foo`; every dropped constraint is collected and printed. apk's own solver is a SAT problem, and a half-implemented one that quietly chose a too-old package would be worse than one that says what it did not check |
| **Package signature verification** | **not built**, and it is the largest *security* gap here. The apko config names a keyring; this build fetches over TLS and checks nothing else. A repository that can serve a package can put anything in the image ([`43`](43-threat-model.md)'s territory), and the `C:` field in the index — which is the control-segment digest apk verifies against — is parsed and carried but not checked |
| **A decompression bound** | **not built.** A package is inflated into memory, and what limits it is the fetcher's reply cap ([`0025`](adr/0025-deflate-so-the-image-build-needs-no-tools.md)) |

## 99.8 What this leaves open

**No runtime has run this image.** GNU tar reads and extracts the layer, the digests are what the
documents say they are, and the layout is the format the spec defines — but no container runtime has
been handed it. This environment has a `docker` client and no daemon, so the step that would have
closed it could not run. That is the same honesty [`92`](92-sbom-report.md) §92.6 applied to the
SBOM ("nothing consumes it") and it is the same fix: run somebody else's tool against it. A
`docker load` or `skopeo copy` in the CI job is the cheapest version.

**And the image CI builds today would not start, for a reason worth naming rather than hiding.**
`--binary` defaults to the running `beck`, which on an ordinary Linux runner is linked against
glibc, and a distroless Wolfi base carries no dynamic loader. [`19`](19-phase-1-report.md) §19.5 is
the precedent — an image config that could not work, invisible until something ran it — so the build
now reads the toolchain's `PT_INTERP` and **says so**: it prints the loader the binary needs and
what to do about it. It warns rather than refuses, because a base image that carries a loader is a
package list away and refusing would be deciding that for everybody. The right binary is §28.2 item
1's static musl build, and until a release produces one there is nothing to pass to `--binary`. This
is also why no image-size number appears in this report: the artefact to measure is not the one
being built.

**The fetch is the one step that has not been executed by hand.** Everything in the CI job was run
locally — the resolve, the unpack, the build, the double-build comparison, the key, the signature,
the verification and its negative control — but this environment's HTTPS goes through a
TLS-intercepting proxy, so the packages were placed in the cache with `curl` and the build was run
`--offline`. The index and the packages are therefore real and the *transport* is not exercised.
[`19`](19-phase-1-report.md) §19.4 item 10 says an artefact nobody has executed is a design
document; this is a job whose one unexecuted step is named, and the first CI run is what executes
it.

**A signature nobody can find is a signature nobody checks.** cosign discovers a signature by
looking up `sha256-<digest>.sig` **in a registry**. This project writes it into the layout's index
under exactly that reference, which is the right place for it to be *copied* from — and until
something pushes, `beck verify` is the only thing that will ever read it.

**The resolver has been exercised against one repository and three packages.** Wolfi's index, and a
dependency closure two deep. Nothing here has met a repository with genuinely competing versions,
a `provides` that two packages both satisfy, or an architecture other than `x86_64`.

The exit criterion is a claim about a person, and no outside developer has read the guide
[`88`](88-read-models-and-pgwire-report.md) published. Of the fourteen bullets, what remains
untouched is **client polish**, and nothing else; the codegen bullet has both of §5.2's code
generators and no heap ([`93`](93-the-native-backends-report.md), [`93`](93-the-native-backends-report.md) §93.14),
Mode B lacks codegen for the same missing heap ([`94`](94-mode-b-report.md) §94.8), and the
playground has rungs A and B and not rung C, which is Phase 4's
([`98`](98-playground-report.md) §98.7). Identity and the playground both finished while this was
being written ([`96`](96-presence-report.md), [`98`](98-playground-report.md)). This bullet's
remainder is a
push and an attestation, and both belong to the release pipeline
[`28`](28-releases-and-deployment.md) is the subject of rather than to the compiler.
