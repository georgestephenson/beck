# Security policy

Beck is a pre-1.0 research compiler and runtime. It is not deployed anywhere by this project, and
nothing here is offered as a product. That does not make a disclosure policy optional: the compiler
is designed to run source written by strangers ([`docs/17`](docs/17-playground.md) §17.3 makes the
compiler the playground's first sandbox), and a project with no policy still receives reports — it
just receives them badly.

This policy follows **ISO/IEC 29147** (vulnerability disclosure) and **ISO/IEC 30111** (handling).
It is deliberately a page.

## Reporting a vulnerability

**Use GitHub's private vulnerability reporting** on this repository — *Security → Report a
vulnerability*. That channel is preferred because it is private by construction, it produces an
advisory record, and it does not depend on an address staying current.

Please include, as far as you have them:

- the version or commit,
- what an attacker gains,
- a reproduction — for a compiler bug, the smallest input that triggers it,
- your assessment of severity, and whether you intend to publish.

Please do **not** open a public issue for a vulnerability. Anything else — a hardening idea, a
question about the threat model — is an ordinary issue and welcome as one.

## What to expect

| | |
|---|---|
| Acknowledgement | within **3 working days** |
| Initial assessment — in scope, severity, whether it reproduces | within **10 working days** |
| Fix or a stated plan | within **90 days** of the assessment, for anything in scope |
| Coordinated publication | with the reporter, on a date agreed with them |

These are the commitments of a small project and are stated as the ceiling rather than the
ambition. If a date is going to slip, the report gets a message saying so before it slips.

We do not operate a bug bounty and cannot pay for reports. Credit is given in the advisory and in
the release notes, under whatever name the reporter asks for, including none.

## Scope

**In scope** — the compiler (`compiler/`), the runtime it targets, the artefacts it generates, and
this repository's own supply chain. Concretely, and in the terms
[`docs/43`](docs/43-threat-model.md) uses: anything an anonymous *author of source* can do to a
process that compiles it, anything an anonymous *client* can do to a running Beck application
beyond what the program allows, any flow that puts a `secret[T]` or a server-only effect on a client
partition, and any way to make a build produce an artefact that does not correspond to its source.

**Out of scope** — and stated so that a report is not written for nothing:

- `phase0/`, which is a measured historical baseline and is not maintained;
- side channels (timing, cache, speculative execution);
- vulnerabilities in dependencies, which belong upstream — though a report telling us we are
  pinning a vulnerable version is welcome and is handled as an ordinary issue;
- anything requiring a compromised host, a privileged local attacker, or a malicious operator;
- **the absent controls the project already documents**: identity is dev-mode (an actor is
  self-asserted), there are no per-actor quotas, no connection limits and no origin checks.
  [`docs/42`](docs/42-security-assurance.md) §42.6 records these and
  `compiler/crates/beck-cli/tests/pending_security.rs` asserts each one as an executable statement
  of what is missing. A report that one of them is missing is welcome as an issue and is not a
  vulnerability report — we know, it is written down, and the tests go red when it stops being true;
- denial of service against a service *you* run using Beck's defaults, for the same reason;
- reports generated by scanning tools with no analysis attached.

The boundary between the last two bullets and a real finding is judgement, and the judgement errs
towards treating a report as real. If you are unsure, report it.

## Memory safety

In CISA and the FBI's terms (*Product Security Bad Practices*, which asks manufacturers of software
written in memory-unsafe languages to publish a memory-safety roadmap), Beck's roadmap is short
because the work was done at the start rather than scheduled:

**Every line of first-party code in this repository is Rust with `unsafe` forbidden at the
workspace root**, and all ten crates inherit that lint — inheritance is what makes a workspace lint
real, and it is present in every member. There is no `unsafe impl Send`/`Sync` anywhere; every
cross-thread type is auto-derived, so the compiler is the reviewer. The network-facing tier — the
parser, the protocol decoder, the patch encoder — therefore has no unsafe code to prioritise, which
is what a roadmap of this kind is for.

The limit of that claim, stated in the same breath: `forbid(unsafe)` covers first-party code only.
The dependencies underneath the network edge — tokio, hyper, tungstenite, redb — are not
`forbid(unsafe)`, and the answer for them is the ordinary one: pinned versions, a `cargo deny`
advisory gate with an **empty** ignore list, `yanked = "deny"`, no git dependencies, and upgrade
discipline. Not an absence of unsafe code.

We do not run Miri as routine CI and say so deliberately: its yield against a `forbid(unsafe)`
workspace is close to nil, and the verify-rust-std campaign — 16,748 proof harnesses over the
standard library, **zero** previously-unknown memory-safety vulnerabilities found — is the evidence
for aiming verification elsewhere. [`docs/42`](docs/42-security-assurance.md) §42.3 has the full
argument, and §42.9 aims it at the placement solver's security invariants instead.

## What Beck does not claim

Written down because the word "secure" invites overclaiming, and the longer version is
[`docs/42`](docs/42-security-assurance.md) §42.10: Beck is not a verified compiler in the CompCert
sense, makes no claim about side channels, cannot vouch for arbitrary FFI, and contains no statement
about a *program's* semantics being secure — only about its flows being contained.
